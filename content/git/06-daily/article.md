## 入れてはいけないもの

`git add .` は便利ですが、プロジェクトのフォルダには、履歴に入れてはいけないものも混ざっています。

| 入れないもの | 理由 |
| --- | --- |
| `node_modules/` | 取り寄せた部品。何万ファイルもあり、`npm install` で再生成できる |
| ビルドの出力(`dist/` など) | 元のコードから作り直せる |
| パスワード、APIキー(`.env` など) | GitHub に上げたら世界中に公開される |
| OSが勝手に作るファイル(`.DS_Store`、`Thumbs.db`) | 自分の環境にしか意味がない |

**パスワードを push してしまう**のは、初心者が起こす事故でいちばん危険なものです。履歴に残るので、あとで消しても見られます。「一度 push したものは公開されたと考える」が鉄則です。

## .gitignore

無視するものを `.gitignore` というファイルに書いておくと、Git はそれらを最初から見なかったことにします。`git add .` しても入りません。

```sh
echo "node_modules/" > .gitignore
git add .
git status
```

`.gitignore` 自体はコミットします。チームの全員で同じものを無視するためです。

書き方は1行1パターンです。

```
node_modules/
dist/
.env
*.log
```

`/` で終わるとフォルダ、`*.log` のように `*` を使うと「.log で終わる全部」です。GitHub でリポジトリを作るとき、言語を選ぶと定番の `.gitignore` を用意してくれるので、最初はそれを使えば十分です。

## コミットの粒度

「1つのコミットには、1つのことを」が目安です。

- よい: 「写真を追加」「リンク切れを直す」「文章を推敲」の3コミット
- よくない: 1日の終わりに全部まとめて「今日の作業」1コミット

小さく分けておくと、履歴が読みやすく、問題のコミットだけ戻すこともできます。コミットはタダなので、迷ったら分けてください。

## よくあるつまずき

**push したのに GitHub が変わらない**
コミットしていません。`git status` を見て、`git add` → `git commit` をしてから `git push` です。

**`git push` が「送り先が決まっていない」と言う**
初回だけ `git push -u origin main` です。

**`git push` が拒否された(rejected)**
GitHub 側に、手元にないコミットがあります(別のパソコンや GitHub の画面で変更した)。先に `git pull` で取り込んでから push します。

**間違えて `add` した**
`git restore --staged ファイル`。

**編集をなかったことにしたい**
`git restore ファイル`。取り消せないので注意。

**`.git` フォルダを消してしまった**
履歴が全部消えます。GitHub に push してあれば `git clone` でやり直せます。push は保険です。

## チームでの流れ

1人のときの「編集 → add → commit → push」に、ブランチと**プルリクエスト**が加わります。

1. `git switch -c 作業名` でブランチを作る
2. 編集 → add → commit を繰り返す
3. `git push -u origin 作業名` でブランチごと push
4. GitHub の画面で「プルリクエスト」を作る。「このブランチを main に取り込んでください」という申請で、他の人がコードを見てコメントできる
5. 問題なければ GitHub 上で merge。`main` が更新される
6. 手元で `git switch main` → `git pull` で最新を取り込む

プルリクエストは Git の機能ではなく GitHub の機能ですが、チーム開発ではここが中心になります。

## まとめ

- `node_modules`、ビルド出力、パスワードは履歴に入れない。`.gitignore` に書く
- 一度 push したものは公開されたと考える
- 1コミット1つのこと。小さく何度でも
- 困ったらまず `git status`。push は保険、こまめに
