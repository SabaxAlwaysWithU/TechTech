## 公開してからが本番

レッスン「公開先の種類」では、どこで動かすかを選びました。でも、VPS(仮想サーバー)を借りてアプリを置いただけでは、まだ安心して使えるサイトにはなりません。

お店にたとえると、建物(サーバー)を借りて商品(アプリ)を並べたあとにも、受付の人、防犯の鍵、閉店中に倒れた人を起こす仕組み、遠くのお客さんのための支店が要ります。このレッスンでは、そうした**サーバーの裏側**の4つの役を見ます。

```
ブラウザ ─→ CDN ─→ 入口(nginx など)─→ アプリ(Django / Express)─→ データベース
              支店      受付 + 鍵(証明書)      動かし続ける仕組みが見張る
```

それぞれの通信の細かい中身は、ネットワーク分野の「Webサーバーの裏側」と「HTTPS と証明書」でも扱っています。ここでは「構成を決めるときに、何を選ぶか」に絞ります。

## 1. 入口: Web サーバー

ブラウザからの接続を最初に受けるのが **Web サーバー**(nginx、Apache、Caddy)です。主な仕事は3つです。

- **静的なファイルを返す**: 画像や CSS は、アプリを通さずにそのまま返すほうが速い
- **取り次ぐ**(リバースプロキシ): `/api/` などの、アプリが答えるべき問い合わせを、後ろの Django や Express に渡す
- **HTTPS の暗号をほどく**: 証明書を持ち、暗号化された通信をここで受ける

アプリ(Django や Express)も直接ブラウザに答えられますが、多くの人からの接続をさばいたり、ファイルを速く返したりするのは Web サーバーのほうが得意です。そこで、前に Web サーバーを置くのが定番になっています。

| | 特徴 |
| --- | --- |
| nginx | 速くて軽い定番。リバースプロキシの設定例がいちばん多い |
| Apache | 古くからの定番。レンタルサーバーで多い |
| Caddy | 設定が短く、証明書を自動で取ってくれる |

## 2. 鍵: HTTPS の証明書

今は、公開するサイトはすべて HTTPS にするのが当たり前です。HTTP のままだと、ブラウザが「保護されていない通信」と表示し、入力したパスワードも盗み見られる可能性があります。

自分のサーバーなら、無料の **Let's Encrypt** が定番です。有効期限が90日と短いので、**自動で更新する設定**(certbot など)を必ず入れます。更新を忘れて期限が切れると、ネットワーク分野で見た `certificate has expired` のエラーになり、誰もサイトを見られなくなります。

会社の決まりで、会社の実在確認まで含んだ**有料の証明書**を使うこともあります。

## 3. 動かし続ける: プロセスの管理

ターミナルで `npm start` や `python manage.py runserver` を打てば、アプリは動きます。でも、そのままでは:

- ターミナルを閉じたり、ログアウトしたりすると止まる
- サーバーが再起動すると、止まったまま
- エラーで落ちても、誰も起こさない

そこで、アプリを「サービス」として見張ってもらいます。

- **systemd**: Linux 分野で使った `systemctl` の仕組みです。サーバーの起動時に自動で始め、落ちたら起こし直す設定ができます
- **Docker**: アプリと、動くのに必要なもの(Python の版、ライブラリなど)を「コンテナ」という箱にまとめます。手元でも本番でも同じ箱が同じように動くので、「自分のパソコンでは動いたのに」が減ります。再起動の決まりも書けます

## 4. 支店: CDN

サーバーが東京にあると、ヨーロッパの利用者には、通信が地球を半周して届きます。また、SNS で話題になってアクセスが急に増えると、1台のサーバーでは返しきれなくなります。

**CDN**(コンテンツ配信ネットワーク)は、世界中にあるサーバーに画像やページのコピーを置き、利用者に近いところから返す仕組みです。Cloudflare などが有名です。本体のサーバーに来る問い合わせが減るので、急な増加にも強くなります。

利用者が国内の決まった人たちで、数も多くなければ、CDN なしでも十分です。

## PaaS が肩代わりしているもの

ここまでの4つを、全部自分で用意するのは大変です。公開先の種類によって、誰がやるかが変わります。

| | VPS | PaaS(Render など) | 静的ホスティング(GitHub Pages など) |
| --- | --- | --- | --- |
| 入口 | 自分で置く | サービス | サービス |
| 証明書 | 自分で(自動更新の設定も) | サービス | サービス |
| 動かし続ける | 自分で(systemd / Docker) | サービス | 不要(ファイルだけ) |
| CDN | 必要なら自分で | 必要なら | 最初から含まれる |

PaaS が VPS より高めでも選ばれるのは、この裏側の手間をまとめて引き受けてくれるからです。逆に VPS は、全部自分で決められる自由と、全部自分の責任、の両方を持っています。

## ほかにもある裏側の仕事

- **環境変数**: データベースのパスワードや API の秘密の鍵は、コードに書かず、サーバーの設定(環境変数)に置く。コードは GitHub で公開されることがあるため
- **ログ**: 何が起きたかの記録。エラーの原因を探すときに読む(Linux 分野の `journalctl`)
- **バックアップ**: データベースは毎日などの決まった間隔で写しを取り、別の場所に置く
- **監視**: サイトが止まったら知らせてくれる仕組み。止まったことに、利用者より先に気づく

## まとめ

- 入口の Web サーバー(nginx など)は、ファイルを返し、アプリに取り次ぎ、HTTPS を受ける
- 証明書は Let's Encrypt が定番。自動更新を必ず設定する
- アプリは systemd や Docker で見張り、落ちたら起こし、再起動しても動くようにする。手で起動したままにしない
- 遠くの利用者や急なアクセスには CDN
- PaaS や静的ホスティングは、これらの多くを肩代わりしてくれる。VPS は全部自分で決め、全部自分で面倒を見る
