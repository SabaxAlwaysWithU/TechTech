## 厨房の作り方

バックエンドは、ブラウザから届いたリクエストを受け取り、ログインを確かめ、データベースに読み書きし、結果を返す「厨房」です。

厨房を作るにはまず**言語**を選び、次にその言語の**フレームワーク**を選びます。フレームワークは「URLごとに処理を振り分ける」「DBとやりとりする」「ログインを扱う」といった、どのアプリにも必要な部分を用意してくれます。

## 言語とフレームワークの対応

| 言語 | フレームワーク | 特徴 |
| --- | --- | --- |
| JavaScript / TypeScript | Express、Hono、NestJS | フロントと同じ言語で書ける。Node.js で動く |
| Python | Django、FastAPI、Flask | 読みやすい。データ分析や機械学習と相性がよい |
| Ruby | Ruby on Rails | 「決まりに従えば速く作れる」。スタートアップで実績 |
| PHP | Laravel | レンタルサーバーで動く。受託開発で多い |
| Java / Kotlin | Spring Boot | 企業システムの定番。堅い |
| Go | Gin、Echo | 速くて軽い。インフラ系のツールに多い |

言語で迷ったら、**フロントと同じ JavaScript(Node.js)** か、**読みやすい Python** のどちらかにすると、学ぶことが減ります。

## 薄いか、全部入りか

同じ言語の中でも、フレームワークには2つの性格があります。

**薄い(マイクロ)フレームワーク**は、最低限の仕組みだけを提供し、あとは自分で組み合わせます。Express、Hono、FastAPI、Flask がこちらです。小さなAPIや、構成を自分で決めたいときに向きます。

**全部入り(フルスタック)フレームワーク**は、ログイン、管理画面、DB操作、メール送信まで最初からそろっています。Django、Rails、Laravel、NestJS、Spring がこちらです。「よくあるWebサービス」を一式作るなら、こちらのほうが速いです。

```
小さなAPIを1つ作る ─────── 薄い(Express / FastAPI)
会員制サービスを一式作る ── 全部入り(Django / Rails / Laravel)
```

## API という考え方

最近のバックエンドは、HTMLを返すのではなく、**データだけを JSON で返す**ことが多くなっています。これを **API** と言います。

```
ブラウザ ──「/api/products をください」──→ サーバー
ブラウザ ←── {"products": [{"name": "マウス", ...}]} ── サーバー
```

画面はフロントエンド(React など)が組み立て、バックエンドはデータの出し入れに専念します。フロントとバックを分けて作れるので、スマホアプリからも同じAPIを使える、といった利点があります。FastAPI や Hono は、この「API専用」の用途で特に選ばれます。

## 書かずに借りる: BaaS

もう1つの選択肢が **BaaS**(Backend as a Service)です。**Firebase** や **Supabase** が代表で、ログイン、データベース、ファイル保存、リアルタイム更新をサービスとして提供します。自分でサーバーのコードを書かず、ブラウザから直接これらを呼び出します。

| | 自分で書く | BaaS を借りる |
| --- | --- | --- |
| 速さ | 作るのに時間がかかる | 数日で形になる |
| 自由度 | 何でもできる | サービスの範囲内 |
| 費用 | サーバー代 | 無料枠あり。増えると従量課金 |
| 向いている | 独自の処理が多い、大規模 | 個人開発、試作、少人数 |

「まず動くものを早く作って試したい」なら BaaS、「仕組みを学びたい」「独自の処理が多い」なら自分で書く、が目安です。

## まとめ

- バックエンドは言語を選び、その言語のフレームワークを選ぶ
- 迷ったら Node.js(フロントと同じ)か Python(読みやすい)
- 薄い(Express / FastAPI)は小さなAPI向け、全部入り(Django / Rails)は一式作る向け
- 自分で書かずに Firebase / Supabase を借りる道もある
