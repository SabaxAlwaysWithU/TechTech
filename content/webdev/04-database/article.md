## 食材庫にも種類がある

冷蔵庫、冷凍庫、常温の棚。食材によって保管場所を変えるように、データにも向いた保存先があります。SQL分野で学んだ「表の形のデータベース」は、その中の1種類です。

## RDB: 表で保存する

**RDB**(リレーショナルデータベース)は、データを表(テーブル)で持ち、SQLで操作します。SQL分野で練習したのがこれです。項目が決まっているデータ、表同士がつながっているデータに強く、**Webアプリの保存先の第一候補**です。

| 名前 | 特徴 |
| --- | --- |
| **PostgreSQL** | 機能が豊富で、無料で、どのクラウドでも使える。迷ったらこれ |
| **MySQL / MariaDB** | 長い実績。WordPress など多くのサービスの裏にある。PostgreSQL とほぼ同じ役割 |
| **SQLite** | ファイル1つで動く。設定不要。個人開発、学習、小さなアプリ向け。練習場で使っているのもこれ |

SQLite と他の2つの違いは「サーバーかどうか」です。PostgreSQL と MySQL は別のプロセスとして動き、ネットワーク越しに複数のアプリから使えます。SQLite はアプリの中でファイルを直接読み書きするので、手軽ですが、同時にたくさんの書き込みが来る用途には向きません。

```
1人で作る、利用者が少ない ──── SQLite
本番で使う、利用者が増える ─── PostgreSQL(または MySQL)
```

## NoSQL: 表以外の形で保存する

表の形に合わないデータのために、別の形で保存するデータベースがあります。まとめて **NoSQL** と呼びます。

**MongoDB**(ドキュメント型)は、JSON のような「文書」をそのまま保存します。商品ごとに項目が違う、途中で項目が増える、といった**形が定まらないデータ**に向きます。表のように事前に列を決めなくてよい反面、表同士をつなぐ JOIN のような操作は苦手です。

**Redis**(キー・値型)は、名前と値の組をメモリ上に保存します。ディスクではなくメモリなので桁違いに速く、**一時的なデータ**(ログイン状態、ランキング、よく読むデータの写し)に使います。メインの保存先にはしません。消えても作り直せるものだけを入れます。

| | RDB | MongoDB | Redis |
| --- | --- | --- | --- |
| 形 | 表 | 文書(JSON) | キーと値 |
| 得意 | 決まった項目、表のつながり | 形が変わるデータ | 速さ、一時データ |
| 例 | 顧客、注文、商品 | ログ、設定、形が違う商品情報 | セッション、キャッシュ |

多くのアプリは RDB だけで足ります。NoSQL は「RDB で困ったときに足す」ものと考えてください。

## BaaS のデータベース

Firebase の **Firestore** や **Supabase** のDB(中身は PostgreSQL)は、ブラウザから直接読み書きできます。サーバーのコードを書かずに保存ができるので、BaaS を選んだときはこれを使います。

## ORM: SQLを書かずに操作する

バックエンドのコードからDBを使うとき、SQLを文字列で組み立てる代わりに、プログラムの書き方でDBを操作する道具が **ORM** です。**Prisma**(Node.js)、Django の ORM、Rails の ActiveRecord などがあります。

```js
// SQL:  SELECT * FROM products WHERE price > 10000
const items = await prisma.product.findMany({ where: { price: { gt: 10000 } } });
```

便利ですが、裏で何のSQLが動いているかを想像できると、遅い処理に気づけます。SQL分野の知識はここで活きます。

## まとめ

- Webアプリの保存先の第一候補は RDB。迷ったら PostgreSQL
- 個人開発・学習なら SQLite で十分
- MongoDB は形が定まらないデータ、Redis は速さが必要な一時データ
- NoSQL は RDB で困ったときに足す
