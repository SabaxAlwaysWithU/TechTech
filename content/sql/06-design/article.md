## 1枚の表に全部書くと何が困るか

注文の記録を、1枚の表にまとめて書いたらどうなるでしょう。

| 注文番号 | 顧客名 | 都道府県 | 商品名 | 価格 | 数量 |
| --- | --- | --- | --- | --- | --- |
| 1 | 佐藤 太郎 | 東京都 | ノートパソコン | 128000 | 1 |
| 1 | 佐藤 太郎 | 東京都 | マウス | 2500 | 1 |
| 3 | 佐藤 太郎 | 東京都 | USBメモリ | 1800 | 3 |

一見わかりやすいのですが、困ったことが3つ起きます。

1. **同じことを何度も書く**: 佐藤さんの名前と住所が、注文のたびに繰り返されます。
2. **直すときに漏れる**: 佐藤さんが引っ越したら、何十行もの「東京都」を全部直す必要があります。1行でも直し忘れると、住所が2つある状態になります。
3. **消すと一緒に消える**: 佐藤さんの注文をすべて削除すると、佐藤さんという顧客の情報も消えてしまいます。

原因は、「顧客のこと」と「注文のこと」と「商品のこと」が1枚に混ざっていることです。

## 表を分ける

解決策は、種類ごとに表を分けて、番号でつなぐことです。この分野のデータベースはまさにそうなっています。

| 表 | 1行が表すもの |
| --- | --- |
| `customers` | 1人の顧客 |
| `products` | 1つの商品 |
| `orders` | 1回の注文(誰が、いつ) |
| `order_items` | 注文の中の1品目(どの注文で、何を、何個) |

顧客の名前と住所は `customers` 表に1回だけ書きます。`orders` 表には名前の代わりに `customer_id`(顧客の番号)だけを書きます。こうすれば、引っ越しのときは `customers` の1行を直すだけで済みます。

このように、重複をなくして表を分けることを**正規化**と呼びます。

## 外部キー: 他の表を指す番号

`orders.customer_id` のように、**他の表の主キーを指している列**を**外部キー**(フォーリンキー)と言います。

```sql
CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL REFERENCES customers(id),
  ordered_at TEXT NOT NULL,
  status TEXT NOT NULL
);
```

`REFERENCES customers(id)` が「この列は `customers` 表の `id` を指しています」という宣言です。これを書いておくと、存在しない顧客番号を注文に入れようとしたときにデータベースが止めてくれます(設定によります)。

外部キーでつながった表は、レッスン4の `JOIN` で元の1枚に戻せます。「分けて保存し、使うときにつなぐ」のがデータベースの基本的な考え方です。

## 1対多

顧客1人に対して注文は何件もあります。この関係を **1対多** と言い、「多」の側(`orders`)に外部キーを置きます。

```
customers (1) ──< orders (多) ──< order_items (多)
products  (1) ──< order_items (多)
```

`order_items` は `orders` と `products` の両方に外部キーを持っています。「どの注文の、どの商品か」を2つの番号で表しているわけです。

## 表を作る: CREATE TABLE

表を設計したら、`CREATE TABLE` で作ります。列ごとに名前と型を書き、主キーには `PRIMARY KEY`、空を許さない列には `NOT NULL` を付けます。

```sql
CREATE TABLE reviews (
  id INTEGER PRIMARY KEY,
  product_id INTEGER NOT NULL REFERENCES products(id),
  score INTEGER NOT NULL,
  comment TEXT
);
```

型は、整数なら `INTEGER`、文字なら `TEXT` を使います。

## まとめ

- 1枚の表に全部書くと、重複、直し漏れ、消し過ぎが起きる
- 種類ごとに表を分け、番号でつなぐ(正規化)
- 他の表の主キーを指す列が外部キー。`REFERENCES` で宣言する
- 1対多の関係では、多の側に外部キーを置く
